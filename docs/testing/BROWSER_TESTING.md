# 브라우저 테스트 시나리오

실제 브라우저에서 화면·숫자·동선을 확인할 때 이 문서를 기준으로 한다. 화면과 분기는 `USER_FLOW.md`, 문구와 레이아웃은 `DESIGN.md`·`UX_GUIDE.md`를 따른다. 이 문서와 화면이 다르면 위 문서와 코드가 맞는지 먼저 확인하고, 이 문서를 고친다.

- 범위: 공개 화면 `/`(랜딩)·`/demo`(데모)·`/login`(로그인), 로그인하지 않은 `/dashboard`·`/settings`, `/auth/*`의 실패·거절 경로. 실제 구글 로그인 이후는 자동화하지 않고 아래 "수동 확인"으로 본다. 로그인 이후 화면은 라우트가 생기면 "추가할 시나리오"에서 옮겨 온다.
- 기대값은 데모 fixture(`src/lib/demo/fixture.ts`)를 `buildDashboard`에 넣어 계산한 값이다. 기준일 `DEMO_TODAY = 2026-10-05`, 데이터 2026-06~09(4개월), 카드 2장(생활비 카드 · 온라인 쇼핑 카드). fixture·탐지 규칙·포맷 함수가 바뀌면 이 문서의 숫자를 먼저 갱신한다.

## 실행 환경
작업을 마칠 때 `/browser-test`로 돌린다(`/review`가 화면 변경이 있으면 요구한다). 명령은 아래 실행기를 쓴다.

```bash
scripts/browser-test/run.sh          # 전체
scripts/browser-test/run.sh s2 s3    # 일부만
```
- `run.sh`가 하는 일: 3100 포트가 비었는지 확인 → `NEXT_PUBLIC_SITE_URL=http://localhost:3100`·`APP_MODE=mock`으로 `npm run build`(Origin 검사·OAuth 복귀 주소가 3100을 쓰게 하고, `.env`가 live여도 mock 화면으로 돌린다) → `next start -p 3100` → 서버 위치가 이 저장소인지 확인 → 각 시나리오 앞에 `lib.js`를 붙여 dev-browser(`--browser assetomy-test --headless`)로 실행 → `PASS`·`FAIL` 집계 → 자기가 띄운 서버만 끈다. FAIL이나 스크립트 오류가 있으면 exit 1.
- `scripts/browser-test/s1-*.js`~`s7-*.js`는 아래 S1~S7을 옮긴 것이다. 기대값을 바꾸면 이 문서와 스크립트를 함께 고친다. 판정은 항목마다 `PASS`/`FAIL` 한 줄로 출력한다.
- 화면을 따로 살펴볼 때는 서버를 3100에 띄우고 도우미를 붙여 쓴다.
  ```bash
  cat scripts/browser-test/lib.js - <<'EOF' | dev-browser --browser assetomy-test --headless --timeout 90
  await go("/demo");
  check("총지출", norm(await section("총지출").innerText()).includes("1,517,200원"), "");
  EOF
  ```
- 도구: [dev-browser](https://github.com/sawyerhood/dev-browser) 0.2.9(`npm install -g dev-browser`). 스크립트는 QuickJS 샌드박스에서 돌고(import 불가) `page`는 Playwright Page다. 스크린샷은 `await saveScreenshot(await page.screenshot({ fullPage: true }), "s1.png")` → `~/.dev-browser/tmp/`.

### 주의할 점
- 프로덕션 서버(`next start`)에서는 Playwright의 `networkidle`이 오지 않는다(남은 요청이 0건이어도). 이동은 `go()`를, 클릭 이동 뒤에는 `settle()`을 쓴다. `load` 뒤 직접 센 요청이 0.5초 동안 0건이면 안정된 것으로 본다.
- `lib.js`는 요소 대기 5초, 이동 대기 60초로 둔다. 이유: locator가 틀리면 Playwright 기본값(30초)만큼 기다리다 스크립트 전체가 결과 없이 끝나고, 서버를 막 띄운 뒤 첫 이동은 5초를 넘는다.
- `run.sh`는 `APP_MODE=mock`을 강제한다. 이유: live로 빌드하면 레이아웃이 Vercel Analytics(`/_vercel/insights/script.js`)를 넣는데, 이 경로는 Vercel에서만 제공돼 로컬에서 404가 나고 모든 시나리오의 콘솔·네트워크 오류 검사가 실패한다(2026-10-13, 수동 결제 확인으로 `.env`가 live였을 때 FAIL 9).
- 3100 포트를 쓴다. 이유: `.claude/worktrees/*`의 다른 세션이 3000에 서버를 띄워 두는 일이 있고, 그러면 내 서버는 `EADDRINUSE`로 뜨지 못하는데 테스트는 그 worktree 화면을 상대로 통과해 버린다.
- 서버는 `lsof -ti tcp:3100 -sTCP:LISTEN | xargs kill`로 내가 띄운 것만 끈다(`-sTCP:LISTEN`이 없으면 그 포트에 붙은 다른 프로세스까지 잡힌다). `pkill -f "next dev"`는 자식 `next-server`를 남긴다. `dev-browser stop`은 다른 세션의 브라우저까지 끄므로 쓰지 않는다(`run.sh`는 `--idle-timeout 5m`으로 자기 브라우저를 닫는다).
- 섹션은 `<h2>` 제목으로 찾는다(`section(...)`). 제목: `총지출`, `카테고리`, `가장 많이 쓴 곳`, `일별 지출`, `확인이 필요한 지출`, `월별 추세`, `이번 달 요약`, `내 카드로 확인해 보세요`. 랜딩은 `요금`, `숫자는 코드가 계산하고, 요약은 문장으로 정리해요`.
- 랜딩은 등장 모션(`reveal`) 때문에 화면 밖 구역이 `opacity: 0`이다. 전체 페이지 스크린샷으로 배치를 볼 때는 `await page.emulateMedia({ reducedMotion: "reduce" })` 뒤에 찍는다. 모션 자체는 스크롤한 뒤 `getComputedStyle(el).opacity`로 확인한다.
- 클라이언트 이동 직후 `page.title()`은 잠깐 빈 문자열이다(Next 16이 metadata를 스트리밍으로 넣음). `await page.waitForFunction(() => document.title !== "")` 뒤에 확인한다.
- dev 서버에서는 Next.js 개발 도구(`NEXTJS-PORTAL`)가 Tab 순서 첫 번째에 끼어든다. S6의 Tab 검사는 이를 건너뛴다.
- Next.js의 경로 알림(`#__next-route-announcer__`)도 `role="alert"`다. 화면의 에러 안내는 `main` 안에서만 찾는다.
- dev-browser 샌드박스에는 `page.request`가 없다. 다른 Origin 요청은 `http://127.0.0.1:3100` 페이지에서 폼을 만들어 `localhost:3100`으로 제출해 재현하고(실제 CSRF와 같은 모양), 같은 Origin 요청은 `page.evaluate`의 `fetch`로 보낸다. 의도한 거절 응답(403·400·405)은 확인 뒤 `logs`를 비운다.
- 구글 로그인 화면(`accounts.google.com`)에 도착한 뒤는 보지 않는다. 계정 선택·동의는 자동화하지 않는다(실제 계정이 필요하고 봇 탐지에 걸린다).
- 샌드박스의 `new URL(...).pathname`은 믿을 수 없다(맞는 URL에서도 비교가 실패했다). 경로는 `page.url().replace(BASE, "")`처럼 문자열로 비교한다.
- `next.config.ts`의 `agentRules: false` 때문에 에이전트가 띄운 `next dev`도 `AGENTS.md`를 고치지 않는다. 테스트 뒤 `AGENTS.md`가 바뀌어 있으면 이 설정이 빠졌는지 확인한다.
- 설치 메모(Node 26): `dev-browser install`이 Playwright 브라우저 압축 해제 중 멈출 수 있다. 받아진 zip(`$TMPDIR/playwright-download-*/`)을 `ditto -x -k <zip> ~/Library/Caches/ms-playwright/<브라우저-버전>`으로 풀고 그 폴더에 `INSTALLATION_COMPLETE`를 만든다. `--headless`에는 `chromium-1208`과 별도로 `chromium_headless_shell-1208`이 필요하다.

## 수동 확인: 월간 요약
자동화하지 않는다(로그인 세션이 필요하다). `npm run dev`(3000)에서 거래가 있는 사용자로 확인한다. DB 확인은 Supabase SQL 편집기에서 본인 `ai_summaries` 행을 본다.
1. 로컬 mock·Free: 제목 줄 바로 아래 전체 폭 `이번 달 요약` 카드(민트 그라데이션·민트 글로우)에 mock 요약(기간·건수·총지출이 총지출 카드의 숫자와 같고 굵게 보인다), `이렇게 절약해 보세요` 팁 목록 세 개(`md:` 이상에서는 오른쪽 열)와 출처 줄(`AI가 가맹점명과 집계로 쓴 요약이에요. 금액은 코드로 계산해요.`), 그 아래 `Pro에서는 확인할 지출 상세와 여러 달 추세까지 요약해요`와 `Pro로 보기`. `Pro로 보기` → 업그레이드 모달. 요약 카드보다 나머지 숫자가 먼저 그려진다.
2. 새로고침 → 같은 문구가 바로 보이고 `ai_summaries`의 `updated_at`이 바뀌지 않는다(다시 만들지 않음). 다른 달을 고르면 그 달 행이 새로 생긴다.
3. `가장 많이 쓴 곳`에서 카테고리 변경 → 카테고리 숫자는 바로 바뀌고, 요약 카드만 스피너·스켈레톤과 `이번 달 요약을 만들고 있어요`를 거쳐 다시 보인다. 그 달 행의 `input_hash`·`updated_at`이 바뀐다.
4. 로컬 mock에서 Pro로 바꾸면(업그레이드 → `결제하기`) 요약이 Pro mock 문구로 바뀌고 `Pro로 보기`가 없다. 행의 `plan`이 `pro`다.
5. 로컬 live(`APP_MODE=live`, `ANTHROPIC_API_KEY`): 요약은 해요체 2~3문장으로 기간·건수·총지출과 비중이 큰 카테고리를 숫자와 함께 말하고, 팁은 1~5개(보통 3~5개)이며 "~해 보세요"처럼 바로 할 수 있는 절약 행동이다. 문장 속 숫자는 화면의 총지출·카테고리·가장 많이 쓴 곳 숫자와 같고, 바로 옆 이름(카테고리·가맹점)의 값이다. `{…}` 같은 자리표시자가 남아 있지 않고, 아낄 금액을 약속하지 않으며, 후보 지출을 "확인이 필요한 지출"처럼 쓰며 "기타" 카테고리를 근거로 삼지 않는다. Free는 가맹점을 콕 집어 후보라고 하지 않고, Pro는 금액이 큰 후보를 가맹점명으로 짚을 수 있다. Pro에서 전월 데이터가 있는 완료된 달(진행 중인 달은 비교하지 않음)은 지난달보다 가장 많이 늘어난·줄어든 카테고리를 금액 차이와 함께 말하고, 그 차이가 `월별 추세`의 카테고리 변화와 같다. 행의 `model`이 `claude-sonnet-5-5`·`claude-opus-5-5`다.
6. 로컬 live에서 `ANTHROPIC_API_KEY`를 비우면 대시보드는 그려지고 요약 카드만 `요약을 만들지 못했어요. 새로고침하면 다시 만들어요.`가 보인다. 서버 로그에는 코드와 사용자 id만 있다.
7. `올린 파일`에서 업로드 삭제 → 그 업로드 거래가 있던 달의 `ai_summaries` 행이 사라진다. 다른 달 행은 남는다.
8. 지난달 비교(카드 이용 기간 12일~다음 달 11일 기준): 9월 23일 명세서(8/12~9/11) 이용 내역만 더 올리면 9월의 총지출 카드에 `8월 내역이 일부만 있어 지난달과 비교하지 않았어요`가 보이고, 요약도 같은 이유를 말하며 8월 대비 증감을 말하지 않는다. 8월 23일 명세서(7/12~8/11)까지 올리면 9월에 `8월보다 … 늘었어요/줄었어요`가 보이고, Pro 요약은 가장 많이 늘어난·줄어든 카테고리를 금액 차이와 함께 짚는다. 진행 중인 달(10월)은 비교하지 않는다.

## 수동 확인: 카드 탭 (UC 17)
자동화하지 않는다(로그인 세션과 실제 명세서가 필요하다). `npm run dev`(3000)에서 `현대` 카드에 9월 23일 명세서(109건 · 1,306,562원)와 10월 23일 명세서(80건 · 1,595,728원)가 있는 사용자로 확인한다. DB는 Supabase MCP `execute_sql`로 본다(가맹점명은 출력하지 않는다).
1. 제목 줄 위 `카드 보기` 탭에 `전체`(현재)와 `현대`가 있다. 전체 탭의 숫자·요약·티저·추세는 이 기능 전과 같다. 375px에서 탭이 넘치면 가로로만 스크롤된다.
2. `현대` → `?card=<id>`, 제목 `현대`, `현대카드 · 월별`, `월 선택`. 달마다 숫자가 그 카드 거래의 그 달 합과 같다. 확인할 지출·월별 추세 카드가 없다. 카드 요약 카드 제목은 `이번 달 요약`이다.
3. `카드 수정` → 모달에 카드사 `현대카드 · 바꿀 수 없어요`, 이름 `현대`, `월별`. `이용 기간` · `12`로 바꾸면 `분석 기준을 바꾸면 이 카드 요약을 다시 만들어요`. `저장` → 모달이 닫히고 `현대카드 · 이용 기간 매달 12일부터`, `명세서 선택`에 `2026년 10월 23일 명세서`·`2026년 9월 23일 명세서`. 다른 카드와 같은 이름이면 저장되지 않고 안내가 보인다. Esc로 닫으면 포커스가 `카드 수정`으로 돌아온다.
4. 10월 23일 명세서: `이용 기간 9/12~10/11`, 총지출 1,595,728원, `9월 23일 명세서보다 +289,166원 늘었어요`, `거래 80건 · 반영 기간 9/12~10/11`. 일별은 9/12부터 10/11까지다. 카드 요약 제목 `이번 명세서 요약`.
5. 9월 23일 명세서: 총지출 1,306,562원, `거래 109건 · 반영 기간 8/12~9/12`, `이용 기간 8/12~9/11`, 지난 명세서 비교 문장이 없다(8월 명세서 없음).
6. Free: 카드 요약 아래 `Pro에서는 달라진 카테고리까지 요약해요` + `Pro로 보기`, 달라진 카테고리 카드는 없다. 페이지 소스(RSC payload)에 `categoryChanges`가 없다. Pro(로컬 mock 결제): 10월 23일 명세서에 `지난 명세서와 달라진 카테고리`가 보이고, live에서 Pro 카드 요약은 가장 많이 늘어난·줄어든 카테고리를 그 카드의 숫자와 같은 금액 차이로 말한다.
7. 로컬 live: 카드 요약 문장 속 숫자가 화면 숫자와 같고 카드 이름·카드사·결제일 숫자를 말하지 않는다. `card_summaries`에 (카드, `2026-10-23`) 행이 생기고 새로고침해도 `updated_at`이 바뀌지 않는다.
8. `카드 수정`으로 다시 `월별`로 바꾸면 그 카드의 `card_summaries` 행이 모두 지워진다. `올린 파일`에서 그 카드 업로드를 지워도 그 카드 행이 모두 지워진다(전체 탭 `ai_summaries`는 그 달 행만 지워진다).

## 수동 확인: 결제 (UC 09, 12)
자동화하지 않는다(로그인 세션이 필요하다). 모달은 Tab이 안에서 순환하고 Esc·닫기로 닫힌다. 설정에서 닫으면 업그레이드 버튼으로 포커스가 돌아오고, 결제 요청 중에는 닫기와 중복 요청이 막힌다.
1. 랜딩 `Pro 시작하기` → 로그인 → `/dashboard?upgrade=pricing`에서 Free 업그레이드 모달. 닫으면 `/dashboard`로 바뀌고 새로고침해도 모달이 다시 열리지 않는다. Pro가 `/dashboard?upgrade=pricing`에 오면 모달 대신 `이미 Pro를 쓰고 있어요`가 보인다(로그인한 채 `/`에 오면 랜딩 없이 `/dashboard`로 간다).
2. 로컬 mock에서 설정 → `업그레이드` → 예시·`월 6,900원`·해외 가격·해지 안내 → `결제하기` → `/dashboard?checkout=success`의 `Pro가 활성화됐어요` → 설정에 Pro 표시(날짜 문구 없음) → `구독 관리` → 설정에서 Free 표시.
3. 로컬 live+sandbox에서 테스트 카드로 결제 → 결제 완료 안내, `polar listen`으로 받은 `customer.state_changed` 웹훅이 200. 반영 중 안내가 나오면 `새로고침`으로 다시 확인하거나 설정을 연다(설정은 열 때마다 Polar와 동기화한다).
4. live+sandbox의 설정 → `구독 관리` → 포털에서 해지 예약 → 포털의 돌아가기로 설정에 오면 바로 `YYYY-MM-DD까지 Pro로 쓸 수 있어요`(웹훅을 기다리지 않는다). 갱신 예정인 Pro에는 `다음 결제일 YYYY-MM-DD`가 보인다.
5. 운영(deploy): Polar 대시보드의 웹훅 엔드포인트(`/api/webhooks/polar`)는 이벤트를 `customer.state_changed`만 선택한다. 나머지 이벤트는 200으로 무시하므로 받을 필요가 없다.

## 미확인 · 관찰 항목
- 월 선택기 방향키: `onChange`에서 바로 `router.push`를 하므로, 방향키로 값이 바뀌는 환경(Windows·Linux Chrome)에서는 누를 때마다 페이지가 이동할 수 있다. macOS 헤드리스에서는 방향키로 값이 바뀌지 않아 재현하지 못했다. 해당 OS에서 수동으로 확인한다.
