# Architecture Decision Records

## 철학
MVP 한 사이클(랜딩 → 데모 → 로그인 → 대시보드 → 결제 → 배포)을 완주하는 것이 최우선이다. 장치를 넣을지는 한 가지 질문으로 판단한다: **"없으면 돈 계산이 틀리거나, 데이터가 유실되거나, 남의 데이터가 보이는가?"** 아니라고 답할 수 있으면 뺀다. 금액은 코드가 계산하고, LLM은 숫자를 만들지 않는다.

---

### ADR-001: Next.js 16 App Router + Vercel, 읽기는 Server Component·쓰기는 Route Handler
**결정**: Next.js 16(`proxy.ts`), Vercel 함수 리전 `icn1`. 읽기는 Server Component, 쓰기는 Route Handler. 예외는 렌더 중 AI 요약 저장과 결제 상태 재동기화(결제 완료 화면·기간이 지난 Pro·설정 화면) 2개뿐이다.
**이유**: 병렬 업로드·웹훅과 쓰기 패턴을 통일하고 테스트하기 쉽다. 요약을 위한 별도 라우트와 클라이언트 fetch가 필요 없다.
**트레이드오프**: 예외 2개에서 동시 요청 시 같은 달 요약을 중복 생성할 수 있다(비용만 조금 늘고 저장은 하나로 수렴).

### ADR-002: Supabase(Seoul) — 사용자 읽기는 RLS, 쓰기는 서버 쓰기 함수
**결정**: Auth·Postgres·Storage를 Supabase로 통일한다. 사용자는 RLS로 본인 데이터만 select하고, 모든 쓰기는 소유권·상태를 검증하는 service-role RPC로 하고, 사용자 단위 쓰기는 사용자별 advisory lock으로 직렬화한다. Storage에는 사용자 정책을 두지 않는다.
**이유**: 직접 DB·Storage 쓰기로 업로드 상태와 삭제 규칙을 우회하지 못하게 한다.
**트레이드오프**: service-role 사용 범위가 서버 쓰기까지 넓어지므로 RPC마다 소유권 검증과 pgTAP 테스트가 필수다.

### ADR-003: 신용카드 이용내역만 받는다
**결정**: 신용카드 이용내역(승인내역)만 받는다. 체크카드·은행 거래내역·청구서는 거절한다. 예외로 현대카드 명세서 "이용 내역" PDF는 모든 거래가 일시불(과 연회비)이고 명세서 금액과 합계가 일치할 때만 이용내역으로 받는다(ADR-019).
**이유**: 은행 내역과 섞으면 이중 집계되고, 청구서는 할부 회차가 정기결제로 오탐된다. 체크카드는 MVP 범위에서 뺀다. 일시불만 있는 명세서는 이용일·원금이 이용내역과 같아 할부 회차 오탐이 생기지 않는다.
**트레이드오프**: 지원 범위가 좁다. 할부가 섞인 현대카드 명세서는 거절된다.

### ADR-004: 파싱 = 카드사 프로필 코드 우선, 없으면 Claude 매핑 제안 + 사용자 확인
**결정**: 실제 fixture로 검증한 카드사 프로필 코드가 헤더 판별·컬럼 위치·청구서 판별·취소 의미를 결정한다. 프로필로 판정되지 않으면 Haiku가 헤더와 값 패턴(숫자 → 9, 문자 → X)만 보고 컬럼 매핑(이용일·가맹점·금액·승인번호·취소 표시)과 청구서 여부를 제안한다. 서버는 제안을 업로드 행에 저장하고, 사용자는 미리보기를 보고 "이대로 읽기" 또는 취소만 고른다. 확정한 매핑은 (사용자, 헤더 시그니처)별로 저장해 다음에는 확인을 생략한다. 폴백은 취소를 음수 금액으로 표시한 형식만 읽는다. 승인번호 열이 없거나, 취소 표시가 있는데 금액이 양수인 행(원 승인 행에 취소 상태를 표시하는 형식)이 있으면 UNREADABLE이다. PDF는 열 이름이 없어 폴백 대상이 아니다. 프로필로 판정되지 않는 PDF는 UNSUPPORTED_FILE이다.
**이유**: 프로필 2종만으로는 지원 범위가 너무 좁다. AI는 열 위치만 제안하고 금액 해석은 같은 코드가 하므로 숫자는 결정적이다. 값 패턴은 날짜·금액 형식을 알려주지만 실제 값은 담지 않는다. 취소 표기 방식은 헤더와 패턴만으로 알 수 없어서, 틀리면 취소가 두 번 반영되는 해석은 폴백에서 하지 않는다.
**트레이드오프**: 처음 보는 형식은 확인 단계가 하나 늘고, fixture로 검증되지 않아 정확성을 사용자 확인에 기댄다. 매핑이 틀리면 열을 고칠 수 없고 취소만 할 수 있다. 상태 표시형 취소 형식은 프로필이 있어야 읽는다.

### ADR-005: Claude는 분류·폴백 매핑(Haiku)과 월 요약(Free Sonnet · Pro Opus)에만
**결정**: 가맹점 분류와 폴백 매핑 제안은 `claude-haiku-5-5`를 쓴다. 월 요약은 Free가 `claude-sonnet-5-5`, Pro가 `claude-opus-5-5`다. 분류는 사용자 수정값·기존 거래에 없는 가맹점만 200개씩(동시 3개) 보낸다. 실패·누락은 'etc'로 두고 업로드는 계속한다. 요약은 플랜별 DTO에서 만든 월 집계만 입력하므로 Free 요약에는 탐지 상세·추세가 들어가지 않는다. 같은 입력 해시면 재생성하지 않고, 입력 해시에 플랜을 포함해 플랜이 바뀌면 다시 만든다. 해시는 모델 ID·프롬프트·입력으로 만든다(mock과 live가 dev DB를 같이 써도 섞이지 않고, 프롬프트를 고치면 다시 만들어진다). 결과는 숫자를 넣은 2~3문장 요약과 절약 팁 1~5개다. 숫자는 AI가 입력 JSON 경로 자리표시자(`{total}`, `{categories[0].ratio}` 등)로 쓰고, 코드가 입력 값으로 채운다. 자리표시자 밖의 숫자(입력 가맹점명 안의 숫자와 'N월'·'YYYY년' 제외), 입력에 없는 경로, 배열 항목의 이름이 같은 요약·팁 안에 없는 자리표시자, 금지 표현이 있으면 코드가 결과 전체를 버린다. 생성이 실패하면(오류·시간 초과·거절·검증 탈락) 저장하지 않고 실패 안내를 보여준 뒤 다음 조회 때 다시 만든다. 이전 요약은 보여주지 않는다.
**이유**: 결정적이어야 하는 금액·탐지는 코드로 하고, 언어 판단이 필요한 곳에만 LLM을 쓴다. 자리표시자를 쓰면 문장 안에 숫자가 들어가도 값은 코드가 만들어서 LLM이 숫자를 반올림하거나 잘못 더할 여지가 없다. 배열 항목 이름 검사는 자리표시자가 다른 항목에 붙는 실수를 줄인다. 이전 요약을 보여주지 않는 이유는 Pro에서 Free로 바뀐 사용자에게 탐지 상세가 담긴 요약이 보이거나, 바뀐 숫자와 어긋난 문장이 보이지 않게 하기 위해서다. 분류·매핑은 단순하고 Free 사용자 업로드마다 호출되므로 작은 모델로 비용을 낮춘다. Free에도 AI 해석을 보여 활성화를 돕고, 입력 범위와 모델의 차이를 Pro 가치로 쓴다.
**트레이드오프**: Free 활성 사용자마다 월 요약 비용이 든다(Sonnet 5.5 단가는 Opus 5.5의 절반). LLM이 자리표시자를 맞는 이름 옆에 쓰고도 문맥을 틀릴 수는 있다(예: 줄어든 값을 늘었다고 말함). 그래서 전월 차이는 부호 없는 크기만 주고 방향은 `direction`으로 말하게 한다. 조사는 LLM이 단위(원·건·%·개월)를 보고 고른다. 검증에 탈락하면 그 조회에는 요약이 없다. 모델 세 개의 응답을 따로 검증한다. 분류 장애 시 카테고리가 'etc'로 남는다(사용자 수정으로 복구, ADR-017).

### ADR-006: 중복 판정 = 카드 지정 + 거래별 식별자 + 파일 해시
**결정**: fingerprint는 `sha256(cardId|identityScope|sourceEventKey|eventKind)`이다. identityScope는 식별자 종류(예: 승인번호)라서 프로필 경로와 폴백 경로에서 같다. 모든 거래 행에 거래별 식별자가 있는 형식만 지원한다. 예외로 식별자가 없는 현대카드 명세서 PDF 프로필은 identityScope가 `content`이고, sourceEventKey는 `이용일|정규화 가맹점명의 공백을 뺀 앞 12자|금액|같은 내용 안 순번(0부터)`이다. 카드는 첫 성공 업로드의 식별 범위·취소 표기 방식으로 고정한다. 같은 file_hash는 사용자의 어느 카드에 올렸든 no_new로 처리한다.
**이유**: 카드 간 충돌을 막고 실제 동일 거래만 중복 제거한다. 같은 파일을 다른 카드로 올려도 이중 집계하지 않는다. 폴백으로 올리던 형식에 나중에 프로필이 생겨도 같은 거래는 같은 fingerprint가 나온다. 취소 표기 방식이 섞이면 같은 취소가 두 번 반영될 수 있어 카드 단위로 고정한다. 행 순번으로는 서로 다른 파일의 동일 거래를 판정할 수 없다. 반면 같은 날·가맹점·금액 안의 순번은 하루치 거래가 모두 들어 있는 파일끼리 같으므로, 같은 명세서를 다시 받아 올려도(파일 바이트가 달라도) 중복으로 걸러진다. 가맹점명은 앞 12자만 쓰는데, 같은 명세서도 받을 때마다 긴 가맹점명이 잘리는 길이가 다르기 때문이다(실제 파일: 10/12에 받으면 19·21·22자, 10/14에 받으면 20자. 공백을 빼면 16자 이상).
**트레이드오프**: 거래별 식별자가 없는 형식은 검증된 프로필만 지원한다. `content` 범위에서는 같은 내용의 파일을 다른 카드로 지정해 올리면(file_hash가 다르면) 이중 집계를 막지 못하고, 해외 결제처럼 원화 금액이 나중에 바뀐 거래는 다른 거래로 본다. 앞 12자가 같은 다른 가맹점이 같은 날 같은 금액이면 같은 내용으로 세어 순번으로 나뉘므로, 나중에 받은 파일에서 그날 그런 거래가 늘면 가맹점명이 서로 바뀌어 저장될 수 있다(건수·금액은 맞다). 키 규칙을 바꾸면 이미 저장된 거래와 키가 달라지므로, 바꾸기 전 업로드와 겹치는 파일은 그 업로드를 지운 뒤 올린다. 같은 카드에 승인번호 형식과 PDF를 섞어 올릴 수 없다(카드 식별 범위 고정).

### ADR-007: 업로드 = 서버 직접 수신(4MB) + 원본 앱 레벨 암호화
**결정**: 브라우저가 파일을 Route Handler로 보낸다(원본 기준 파일당 4MB). 서버는 AES-256-GCM(파일마다 랜덤 IV)으로 암호화한 뒤 private 버킷에 저장하고, 평문은 메모리에서만 다룬다. 키는 환경변수 `FILE_ENCRYPTION_KEY` 하나다.
**이유**: Vercel 함수 본문 제한(4.5MB) 안에서 받으면 평문이 Storage에 남는 구간이 없다. signed URL 발급과 삭제 후 늦게 도착한 파일의 정리가 필요 없다. 5,000행 상한이면 일반적인 이용내역은 4MB 안에 들어간다.
**트레이드오프**: 4MB를 넘는 파일은 기간을 나눠 받아야 한다. 키 하나가 유출되면 모든 원본이 노출되고, MVP에는 키 교체가 없다. 키를 잃으면 원본을 복구할 수 없다. 거래 데이터는 DB에 평문으로 있다(RLS와 Supabase 기본 암호화로 보호).

### ADR-008: 업로드 처리 = 원자적 claim + lease + 단일 트랜잭션 ingest, 재claim 없음
**결정**: 업로드 행은 사용자 잠금 아래 processing(6분 lease)으로 만들고, needs_mapping→processing(매핑 확인)은 조건부 update로 claim한다. 거래 insert와 상태·결과 갱신은 `ingest_upload` 한 트랜잭션이다. RPC 응답이 불명확하면 상태를 한 번 다시 읽고, 확인할 수 없으면 행을 보존한 채 503을 돌려준다(202·상태 폴링 없음). lease가 만료된 processing은 늦게 도착한 ingest나 정기 작업이 failed로 끝내고 사용자가 다시 올린다. 동시 처리 한도는 lease가 남은 processing만 센다. needs_mapping은 lease를 잡지 않고, 1시간이 지나면 정기 작업이 failed로 끝낸다.
**이유**: 둘 사이에서 실패하거나 동시 이중 처리가 일어나면 완료 거래가 유실될 수 있다. 자동 재claim과 세대 번호 없이도 lease 검사만으로 늦은 커밋을 막을 수 있다.
**트레이드오프**: 함수가 강제 종료되면 사용자가 재업로드해야 한다.

### ADR-009: 삭제·보관 = DB 즉시 삭제 + 12개월 보관 기한 + 정기 정리
**결정**: 업로드 삭제와 전체 삭제는 DB에서 한 트랜잭션으로 즉시 끝내고 원본 삭제를 시도한다. 남은 파일과 no_new/failed 원본은 5분 주기 정기 작업이 "업로드 행이 없거나 종료 상태인 객체"로 판정해 지운다. 거래·요약은 이용일 기준 12개월이 지나면 플랜과 관계없이 지우고, 거래가 모두 사라진 업로드는 행과 원본을 지운다. 보관 기한 밖의 거래는 저장하지 않는다.
**이유**: 업로드 행은 파일 저장 전에 커밋되므로 행이 없는 객체는 언제 지워도 안전하다. "삭제 중" 상태·작업 테이블 없이 Storage 장애를 한 경로로 처리한다. 보관 기한을 두면 민감 데이터 보관을 줄이고 처리방침에 기간을 분명히 쓸 수 있다.
**트레이드오프**: 추세는 최대 12개월까지만 보인다. Storage 삭제에 실패한 원본은 다음 정리까지 남는다. 단일 업로드 삭제 시 다른 파일에서 중복 제외된 거래는 자동 복원되지 않는다(영향 고지와 재업로드 안내).

### ADR-010: 탐지는 규칙 기반 코드
**결정**: 정기결제(서로 다른 달 2개 이상, 간격 28~35일, 금액 ±10%), 중복 결제 의심(같은 날·가맹점·금액, 교통 제외, 1만 원 이상), 고액 결제(양수 구매 20건 이상, 중앙값 × k 초과)를 순수 함수로 구현한다.
**이유**: 결정적이고 테스트 가능하다. 임계값은 오탐을 줄여 신뢰와 Pro 전환 메시지를 지킨다.
**트레이드오프**: 정교함이 제한적이다.

### ADR-011: 플랜 게이팅은 `buildDashboard` DTO 유니온 한 곳
**결정**: Free DTO는 `{ snapshot, mom, partialMonth, teaser }`, Pro DTO는 `{ snapshot, mom, partialMonth, findings, trend }`로 나눈다(`partialMonth`는 ADR-022). 월 요약은 각 DTO만 입력으로 만든다.
**이유**: Server→Client props는 RSC payload로 노출되므로 컴포넌트에서 숨기는 방식은 상세를 새게 한다. 요약 입력을 DTO로 제한하면 요약 문장도 Free에 상세를 담을 수 없다.
**트레이드오프**: Free도 RLS로 자기 거래를 직접 읽을 수 있으므로, 게이팅은 UX 경계이지 데이터 보안 경계가 아니다.

### ADR-012: Polar 결제 + 상태 재조회 + 조회 시작 시각 조건부 저장
**결정**: 웹훅과 success 페이지 모두 Polar의 현재 상태를 다시 조회하고, 조회 시작 시각이 저장된 `synced_from`보다 늦을 때만 저장한다. 첫 실결제는 production active Pro의 첫 확인으로 측정한다(쿠폰·무료 구독 미운영 전제).
**이유**: 웹훅이 실패해도 결제한 사용자가 Free로 남지 않고, 먼저 시작한 조회가 늦게 도착해도 최신 상태를 덮지 않는다. lease와 세대 번호가 필요 없다.
**트레이드오프**: 늦게 시작한 조회가 더 최신이라고 간주한다. 쿠폰을 도입하면 결제 주문 확인으로 바꿔야 한다.

### ADR-013: 측정 = Vercel Analytics(탐색) + `user_metrics`·`upload_attempts`(코호트)
**결정**: 범용 events 테이블 없이, 첫 시도·첫 성공·티저 노출·첫 클릭·첫 결제와 업로드 단계별 결과만 DB에 남긴다.
**이유**: Vercel의 방문자 식별은 24시간 후 폐기되어 여러 날에 걸친 전환을 잴 수 없다. 업로드 행을 지워도 측정 분모가 보존돼야 한다.
**트레이드오프**: 정해진 지표 외의 사후 분석은 어렵다.

### ADR-014: Production = live 고정, Preview = mock 고정
**결정**: `getMode()`는 `VERCEL_ENV`가 production이면 항상 live, preview면 항상 mock이다. 로컬만 `APP_MODE`로 고른다. Preview는 dev Supabase를 쓰고 Anthropic·Polar 키를 넣지 않는다.
**이유**: 키 없이도 step마다 화면을 확인하고, Production이 구조적으로 mock이 될 수 없게 한다.
**트레이드오프**: Preview에서는 실제 LLM·결제를 검증할 수 없어 로컬 live+sandbox와 production 검증을 따로 해야 한다.

### ADR-015: 테스트 = 단위(`npm test`)와 DB 통합(`npm run test:db`) 분리
**결정**: Supabase 없이 도는 단위 테스트와 Supabase 프로젝트가 필요한 통합 테스트(`*.db.test.ts`), pgTAP을 나눈다(ADR-020). 파싱은 익명화한 실제 fixture의 기대 합계와 정확히 일치해야 한다.
**이유**: Stop hook과 기본 AC가 Supabase·네트워크 상태와 무관하게 돌아야 한다. 금액 정확성이 제품의 신뢰 기반이다.
**트레이드오프**: DB를 쓰는 step은 AC에 통합 테스트 명령을 따로 넣어야 한다.

### ADR-016: 탈퇴는 앱 안에서
**결정**: 설정에서 탈퇴하면 전체 삭제와 같은 트랜잭션으로 소비 데이터·측정 이력·카테고리 수정값·매핑·운영 기록을 지우고, 커밋 후 Auth 사용자를 삭제한다. 자동 갱신 예정인 구독이 있으면 거절하고 포털에서 해지하도록 안내한다. 해지 예약 상태면 남은 Pro 기간이 사라진다는 확인을 받는다.
**이유**: 가입이 1클릭이므로 탈퇴도 앱 안에서 끝나야 한다. 자동 갱신을 막아 탈퇴 후에도 결제가 이어지는 일을 없앤다.
**트레이드오프**: 탈퇴 후 다시 가입하면 24시간 업로드 한도가 초기화된다. Polar의 고객 기록은 Polar에 남는다(처리방침에 고지). 탈퇴 뒤 도착한 웹훅은 사용자가 없어 무시한다.

### ADR-017: 카테고리 = 고정 14개 + 가맹점 단위 사용자 수정
**결정**: 카테고리는 고정 14개(식비, 카페·간식, 배달, 교통, 쇼핑, 마트·생활, 구독·정기결제, 주거·통신, 의료·건강, 문화·여가, 여행·숙박, 교육, 금융·보험, 기타)다. 사용자가 가맹점의 카테고리를 바꾸면 (사용자, 정규화 가맹점명)별 수정값을 저장하고, 같은 트랜잭션에서 그 사용자의 같은 가맹점 거래를 모두 갱신한다. 새 거래의 카테고리는 수정값 → 기존 거래의 같은 가맹점 → 고정 규칙(연회비 → 금융·보험) → Haiku 분류 순서로 정한다.
**이유**: 분류 오류와 'etc'를 사용자가 바로잡을 수 있어야 카테고리 분포를 믿는다. 숫자는 코드가 다시 계산한다.
**트레이드오프**: 수정할 때마다 그 달 집계가 바뀌어 요약이 다음 조회 때 다시 생성된다(Sonnet·Opus 호출 증가).

### ADR-018: 가격 = USD 기본 + KRW 가격
**결정**: Pro 상품은 USD $4.99/월을 기본 가격으로 두고 KRW 가격을 추가한다. 랜딩·모달은 KRW로 표시한다. 서버에서 만든 checkout에는 요청자 IP를 `customer_ip_address`로 넘긴다.
**이유**: Polar는 고객 위치로 통화를 고르므로 한국 사용자는 원화로 결제할 수 있다. USD 결제 거부감을 줄인다.
**트레이드오프**: KRW 금액이 아직 미정이다(sandbox는 임시값). 정산은 USD로 될 수 있어 환율에 따라 실수령액이 달라진다. IP 전달을 빠뜨리면 서버 위치 기준 통화로 표시된다.

### ADR-019: PDF = pdfjs-dist로 글자·좌표만 추출 + 카드사 프로필 + 명세서 금액 대조
**결정**: PDF는 `pdfjs-dist`(legacy build, `isEvalSupported: false`)로 쪽별 글자 조각과 좌표만 뽑는다. 한글 CID 글꼴을 읽도록 패키지의 `cmaps/`를 함께 쓰고 함수 번들에 포함한다. 추출은 `lib/pdf/`(I/O)가, 같은 높이의 조각을 한 줄로 묶고 프로필을 적용하는 일은 순수 레이어 `lib/parsing/`이 한다. 첫 프로필은 현대카드 앱·웹의 명세서 "이용 내역" 화면을 최근순으로 PDF 저장한 형식이다. 날짜 줄(`26. 10. 11 (일)`) 아래에 거래 줄(왼쪽 가맹점, 오른쪽 금액+"원")과 결제 방식 줄(`일시불 …`)이 이어진다. 해외 결제는 그 사이에 통화 줄이 있다. 통화 줄은 `(USD:22.00)`이거나, 20자에서 잘린 가맹점명의 나머지에 `,USD:22.00`을 붙인 줄(`SU,USD:22.00`)이며 나머지는 가맹점명에 이어 붙인다. 거래 줄 끝의 `,USD:11.00`도 가맹점명에서 뗀다. 국내 가맹점도 이름이 길면 나머지가 다음 줄로 넘어간다. 거래 줄 바로 다음의 한 줄이 날짜·결제 방식·적립·거래 줄이 아니고 이어 붙여 20자 이하면 가맹점명 나머지로 읽는다. 이어 붙일 때는 공백을 넣어 20자 안이면 공백을 넣고(공백에서 줄이 넘어감) 아니면 그대로 붙인다. 연회비 줄에는 결제 방식 없이 `현대카드…` 줄이 붙는다. 할부가 아니므로 이 경우만 일시불이 아니어도 받고, 카테고리는 분류기 없이 금융·보험으로 둔다(사용자 수정값이 먼저). 취소된 거래는 결제 방식 줄이 `… 0원`이 되고 적립 줄 아래에 `결제 취소 -254,000원` 줄이 붙는다. 이 줄은 같은 날짜 아래 바로 위 거래의 취소(같은 이용일·가맹점, 음수 금액)로 읽는다. 상단 명세서 금액과 거래 금액 합이 정확히 같을 때만 저장한다. 일시불이 아닌 결제 방식, "취소" 표시가 있는 양수 금액 행, 위 거래가 없는 `결제 취소` 줄, 합계 불일치, 구조가 깨진 줄은 UNREADABLE이다. 음수 금액은 취소로 읽는다. `%PDF-` 시그니처가 없거나, 암호가 걸렸거나, 100쪽을 넘거나, 글자가 없거나(스캔), 어느 프로필에도 맞지 않으면 UNSUPPORTED_FILE이다.
**이유**: 사용자가 쉽게 받을 수 있는 형식이 명세서 PDF뿐인 경우가 있다. 카드사가 계산한 명세서 금액과 대조하면 처음 보는 줄(할부·취소 표기)이 섞여도 틀린 숫자를 저장하지 않는다. 화면 인쇄 PDF는 글자 순서가 화면 순서와 달라 좌표로 줄을 다시 묶어야 한다. `unpdf` 서버리스 빌드에는 cmaps가 없어 한글 가맹점명이 빠진다.
**트레이드오프**: 인쇄한 브라우저·앱 버전에 따라 줄 배치가 바뀌면 읽지 못할 수 있다(합계 대조로 거절되고 틀린 값은 저장하지 않음). 할부가 있는 명세서와 처음 보는 취소·통화 표기는 실제 파일로 확인할 때까지 거절될 수 있다(2026-10-14에 받은 파일의 통화 줄·`결제 취소` 줄이 그런 예였다). pdfjs-dist와 cmaps(약 1.6MB)가 서버 번들에 들어간다.

### ADR-020: Supabase = 클라우드 프로젝트에 API로 연결(로컬 Docker 미사용)
**결정**: 로컬 개발도 클라우드 dev 프로젝트(`assetomy-dev`, 서울)에 URL·키로 연결한다. Preview는 같은 dev 프로젝트, Production은 deploy phase에서 만드는 prod 프로젝트를 쓴다. 인증 설정(Google provider · Site URL · Redirect URLs · 이메일 가입 끔)은 프로젝트 대시보드에서 관리하고, `supabase/config.toml`은 마이그레이션·pgTAP용으로만 둔다.
**이유**: Docker 없이 바로 쓸 수 있고, 구글 OAuth 리디렉션 URI를 배포 환경과 같은 형태(`https://<ref>.supabase.co/auth/v1/callback`)로 맞춘다.
**트레이드오프**: 로컬·Preview·DB 통합 테스트가 같은 dev 데이터베이스를 쓴다. 그래서 DB 통합 테스트는 테스트마다 admin API로 임시 사용자를 만들고 끝나면 지우며, pgTAP은 트랜잭션 안에서 돌고 롤백한다. pgTAP은 `supabase test db`(pg_prove를 Docker로 실행) 대신 `scripts/pgtap.sh`가 `supabase db query --linked`(Management API)로 실행한다. 이 경로는 마지막 SELECT 결과만 돌려주므로 테스트 파일은 단언 결과를 임시 테이블에 모아 마지막에 반환한다. 인증 설정이 코드에 없어 prod 프로젝트에 같은 값을 손으로 다시 넣어야 한다. 무료 프로젝트는 오래 쓰지 않으면 일시 정지된다.

### ADR-021: 로그인 = 서버에서 시작하는 구글 OAuth(PKCE) + 폼 POST
**결정**: `/login`의 폼이 `POST /auth/login`으로 `next`를 보내면, Route Handler가 Origin을 검사하고 서버 Supabase 클라이언트의 `signInWithOAuth`로 PKCE 흐름을 시작해 303으로 구글에 보낸다. 복귀 URL은 `lib/origin.ts`로 만든다. `/auth/callback`이 코드를 교환하고, 로그아웃도 `POST /auth/logout` 폼이다. 브라우저용 Supabase 클라이언트는 두지 않는다. 구글 버튼은 Google 브랜드 가이드(흰 바탕 · `#747775` 테두리 · 원래 색 G 로고, "Google로 계속하기")를 따른다.
**이유**: 클라이언트 JS·공개 키 전달 없이 쓰기 패턴(Route Handler + Origin 검사)과 같게 만든다. 복귀 URL을 서버 한 곳에서 정해 Preview·Production이 같은 코드로 돈다. Google 브랜드 가이드 준수는 OAuth 앱 검증 요건이다.
**트레이드오프**: 로그인 버튼에 처리 중 표시가 없다(브라우저가 바로 구글로 이동). 구글 버튼은 디자인 토큰의 Primary 규칙에서 벗어난다(DESIGN "디자인 시스템과 다르게 정한 것").

### ADR-022: 전월 비교 = 카드마다 거래일 범위가 두 달을 덮을 때만
**결정**: `buildMonthComparison`은 진행 중인 달·전월 데이터 없는 달을 빼고, 두 달 중 한 달에라도 거래가 있는 카드마다 첫 거래일이 지난달 1일에서 3일 안쪽, 마지막 거래일이 선택한 달 말일에서 3일 안쪽일 때만 전월 대비를 만든다. 아니면 `mom = null`과 내역이 일부만 있는 달(`partialMonth`, 지난달을 먼저 본다)을 DTO에 넣는다. Pro 추세의 `categoryChanges`와 AI 요약 입력도 같은 결과를 따른다.
**이유**: 카드 명세서 이용 기간은 결제일마다 달라서(사용자 실제 카드: 12일~다음 달 11일) 명세서 한 장만 올려도 두 달에 걸친다. 첫 달은 중간부터라 그대로 비교하면 거의 모든 카테고리가 늘었다고 나온다. 이용 내역 PDF에는 이용 기간이 없고, 업로드의 기간은 새로 들어간 거래만으로 계산해서(ADR-006 중복 제외 뒤) 파일 범위가 아니다. 그래서 순수 함수 안에서 카드별 거래일로 판단한다. 카드마다 보는 이유는 카드별로 결제일이 달라 전체 최소·최대 날짜로는 한 카드의 빈 기간이 가려지기 때문이다. 3일 여유는 그날 거래가 없었던 경우와 이용 기간이 달 경계와 하루 이틀 어긋나는 결제일(예: 전전월 31일~전월 30일)을 위한 것이다.
**트레이드오프**: 카드 중간의 빠진 명세서(7월·9월만 올리고 8월은 안 올림)는 거래가 없는 기간과 구별하지 못해 비교한다. 새로 만든 카드처럼 지난달에 정말 쓰지 않은 카드도 그달을 덮지 않은 것으로 보아 비교를 건너뛴다. 3일 안쪽으로 빠진 날은 덮은 것으로 본다. 추세의 월별 막대는 일부만 있는 달도 그대로 그린다.
