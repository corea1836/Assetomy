# Architecture Decision Records

## 철학
MVP 한 사이클(랜딩 → 데모 → 로그인 → 대시보드 → 결제 → 배포)을 완주하는 것이 최우선이다. 장치를 넣을지는 한 가지 질문으로 판단한다: **"없으면 돈 계산이 틀리거나, 데이터가 유실되거나, 남의 데이터가 보이는가?"** 아니라고 답할 수 있으면 뺀다. 금액은 코드가 계산하고, LLM은 숫자를 만들지 않는다.

---

### ADR-001: Next.js 16 App Router + Vercel, 읽기는 Server Component·쓰기는 Route Handler
**결정**: Next.js 16(`proxy.ts`), Vercel 함수 리전 `icn1`. 읽기는 Server Component, 쓰기는 Route Handler. 예외는 대시보드 렌더 중 AI 요약 저장과 오래된 결제 상태 보완 동기화 2개뿐이다.
**이유**: 병렬 업로드·웹훅과 쓰기 패턴을 통일하고 테스트하기 쉽다. 요약을 위한 별도 라우트와 클라이언트 fetch가 필요 없다.
**트레이드오프**: 예외 2개에서 동시 요청 시 같은 달 요약을 중복 생성할 수 있다(비용만 조금 늘고 저장은 하나로 수렴).

### ADR-002: Supabase(Seoul) — 사용자 읽기는 RLS, 쓰기는 서버 쓰기 함수
**결정**: Auth·Postgres·Storage를 Supabase로 통일한다. 사용자는 RLS로 본인 데이터만 select하고, 모든 쓰기는 소유권·상태·세대를 검증하는 service-role RPC로 한다. Storage에는 사용자 정책을 두지 않는다.
**이유**: 직접 DB·Storage 쓰기로 업로드 상태와 삭제 규칙을 우회하지 못하게 한다.
**트레이드오프**: service-role 사용 범위가 서버 쓰기까지 넓어지므로 RPC마다 소유권 검증과 pgTAP 테스트가 필수다.

### ADR-003: 신용카드 이용내역만 받는다
**결정**: 신용카드 이용내역(승인내역)만 받는다. 체크카드·은행 거래내역·청구서는 거절한다.
**이유**: 은행 내역과 섞으면 이중 집계되고, 청구서는 할부 회차가 정기결제로 오탐된다. 체크카드는 MVP 범위에서 뺀다.
**트레이드오프**: 지원 범위가 좁다.

### ADR-004: 파싱은 카드사 프로필 코드로만, LLM 컬럼 매핑 없음
**결정**: 실제 fixture로 검증한 카드사 프로필 코드가 헤더 판별·컬럼 위치·청구서 판별·취소 의미를 결정한다. 프로필로 판정되지 않는 형식은 UNREADABLE로 거절한다.
**이유**: 검증되지 않은 형식은 어차피 거절하므로 LLM 매핑이 할 일이 없다. 매핑 실패 경로가 사라지고, 외부로 보내는 데이터가 가맹점명과 집계뿐이다.
**트레이드오프**: 새 카드사 형식마다 프로필 코드와 fixture가 필요하다.

### ADR-005: Claude(`claude-opus-5-5`)는 가맹점 분류와 월 요약에만
**결정**: 분류는 사용자의 기존 거래에 없는 가맹점만 200개씩(동시 3개) 보낸다. 실패·누락은 'etc'로 두고 업로드는 계속한다. 요약은 Pro의 월 집계만 입력하며 같은 입력 해시면 재생성하지 않는다.
**이유**: 결정적이어야 하는 금액·탐지는 코드로 하고, 언어 판단이 필요한 곳에만 LLM을 쓴다.
**트레이드오프**: 분류 장애 시 카테고리가 'etc'로 남는다.

### ADR-006: 중복 판정 = 카드 지정 + 거래별 식별자 + 파일 해시
**결정**: fingerprint는 `sha256(cardId|profileIdentityScope|sourceEventKey|eventKind)`이다. 모든 거래 행에 거래별 식별자가 있는 형식만 지원한다. 같은 file_hash는 사용자의 어느 카드에 올렸든 no_new로 처리한다.
**이유**: 카드 간 충돌을 막고 실제 동일 거래만 중복 제거한다. 같은 파일을 다른 카드로 올려도 이중 집계하지 않는다. 행 순번으로는 서로 다른 파일의 동일 거래를 판정할 수 없다.
**트레이드오프**: 거래별 식별자가 없는 카드사 형식은 지원하지 않는다.

### ADR-007: 브라우저 → Storage signed URL 직접 업로드
**결정**: 서버가 업로드 행을 커밋한 뒤 signed upload URL을 발급하고, 브라우저가 Storage로 직접 올린다.
**이유**: Vercel 함수 본문 4.5MB 제한 때문에 큰 파일이 실패한다(대안 없음).
**트레이드오프**: 요청이 3번 오가고, signed URL이 2시간 유효해 삭제 후 늦은 전송이 생길 수 있다(ADR-009로 처리).

### ADR-008: 업로드 처리 = 원자적 claim + lease + 단일 트랜잭션 ingest, 재claim 없음
**결정**: pending→processing 조건부 update로 claim하고 6분 lease를 둔다. 거래 insert와 상태·결과 갱신은 `ingest_upload` 한 트랜잭션이다. RPC 응답이 불명확하면 상태를 다시 조회하고, 확인할 수 없으면 보존한다. lease가 만료된 processing은 정기 작업이 failed로 끝내고 사용자가 다시 올린다.
**이유**: 둘 사이에서 실패하거나 동시 이중 처리가 일어나면 완료 거래가 유실될 수 있다. 자동 재claim과 세대 번호 없이도 lease 검사만으로 늦은 커밋을 막을 수 있다.
**트레이드오프**: 함수가 강제 종료되면 사용자가 재업로드해야 한다.

### ADR-009: 삭제 = DB 즉시 삭제 + 정기 고아 파일 정리
**결정**: 업로드 삭제와 전체 삭제는 DB에서 한 트랜잭션으로 즉시 끝낸다. 원본은 즉시 삭제를 시도하고, 남은 파일·늦게 도착한 파일·no_new/failed 원본은 5분 주기 정기 작업이 "업로드 행이 없거나 종료 상태인 객체"로 판정해 지운다.
**이유**: 업로드 행은 URL 발급 전에 커밋되므로 행이 없는 객체는 언제 지워도 안전하다. "삭제 중" 상태·토큰 만료 추적·작업 테이블 없이 늦은 전송과 Storage 장애를 한 경로로 처리한다.
**트레이드오프**: 남은 원본은 다음 정리까지 최대 몇 분 Storage에 남는다. 단일 업로드 삭제 시 다른 파일에서 중복 제외된 거래는 자동 복원되지 않는다(영향 고지와 재업로드 안내).

### ADR-010: 탐지는 규칙 기반 코드
**결정**: 정기결제(서로 다른 달 2개 이상, 간격 28~35일, 금액 ±10%), 중복 결제 의심(같은 날·가맹점·금액, 교통 제외, 1만 원 이상), 고액 결제(양수 구매 20건 이상, 중앙값 × k 초과)를 순수 함수로 구현한다.
**이유**: 결정적이고 테스트 가능하다. 임계값은 오탐을 줄여 신뢰와 Pro 전환 메시지를 지킨다.
**트레이드오프**: 정교함이 제한적이다.

### ADR-011: 플랜 게이팅은 `buildDashboard` DTO 유니온 한 곳
**결정**: Free DTO는 `{ snapshot, mom, teaser }`, Pro DTO는 `{ snapshot, mom, findings, trend }`로 나눈다. 요약도 Pro일 때만 렌더링한다.
**이유**: Server→Client props는 RSC payload로 노출되므로 컴포넌트에서 숨기는 방식은 상세를 새게 한다.
**트레이드오프**: Free도 RLS로 자기 거래를 직접 읽을 수 있으므로, 게이팅은 UX 경계이지 데이터 보안 경계가 아니다.

### ADR-012: Polar 결제 + 상태 재조회 + 조회 시작 시각 조건부 저장
**결정**: 웹훅과 success 페이지 모두 Polar의 현재 상태를 다시 조회하고, 조회 시작 시각이 저장된 `synced_from`보다 늦을 때만 저장한다. 첫 실결제는 production active Pro의 첫 확인으로 측정한다(쿠폰·무료 구독 미운영 전제).
**이유**: 웹훅이 실패해도 결제한 사용자가 Free로 남지 않고, 먼저 시작한 조회가 늦게 도착해도 최신 상태를 덮지 않는다. lease와 세대 번호가 필요 없다.
**트레이드오프**: 늦게 시작한 조회가 더 최신이라고 간주한다. 쿠폰을 도입하면 결제 주문 확인으로 바꿔야 한다.

### ADR-013: 측정 = Vercel Analytics(탐색) + `user_metrics`·`upload_attempts`(코호트)
**결정**: 범용 events 테이블 없이, 첫 시도·첫 성공·티저 노출·첫 클릭·첫 결제와 업로드 단계별 결과만 DB에 남긴다.
**이유**: Vercel의 방문자 식별은 24시간 후 폐기되어 여러 날에 걸친 전환을 잴 수 없다. 업로드 행을 지워도 측정 분모가 보존돼야 한다.
**트레이드오프**: 정해진 지표 외의 사후 분석은 어렵다.

### ADR-014: Production = live 고정, Preview = mock 고정
**결정**: `getMode()`는 `VERCEL_ENV`가 production이면 항상 live, preview면 항상 mock이다. 로컬만 `APP_MODE`로 고른다. Preview는 dev Supabase를 쓰고 Anthropic·Polar 키를 넣지 않는다.
**이유**: 키 없이도 step마다 화면을 확인하고, Production이 구조적으로 mock이 될 수 없게 한다.
**트레이드오프**: Preview에서는 실제 LLM·결제를 검증할 수 없어 로컬 live+sandbox와 production 검증을 따로 해야 한다.

### ADR-015: 테스트 = 단위(`npm test`)와 DB 통합(`npm run test:db`) 분리
**결정**: Docker 없이 도는 단위 테스트와 로컬 Supabase가 필요한 통합 테스트(`*.db.test.ts`), pgTAP을 나눈다. 파싱은 익명화한 실제 fixture의 기대 합계와 정확히 일치해야 한다.
**이유**: Stop hook과 기본 AC가 Docker 상태와 무관하게 돌아야 한다. 금액 정확성이 제품의 신뢰 기반이다.
**트레이드오프**: DB를 쓰는 step은 AC에 통합 테스트 명령을 따로 넣어야 한다.

## 의도적으로 뺀 것 (다시 넣지 말 것)
| 항목 | 대신 하는 것 |
|---|---|
| 범용 `events` 테이블 | Vercel Analytics + `user_metrics`·`upload_attempts` |
| LLM 컬럼 매핑, 매핑 실패 시 LLM 재시도, 행 샘플 마스킹 | 카드사 프로필 코드(ADR-004) |
| 제외 사유별 집계(SkipBreakdown) | `skipped: number` 하나 |
| 세분화된 업로드 에러 코드 | 업로드 코드 5개 + 허용된 reason + HTTP 상태 |
| `/api/summary` 라우트와 클라이언트 fetch | 대시보드 Server Component에서 생성(Suspense) |
| `documentType` 3값 | 청구서 여부 boolean 판별 |
| 식별자 없는 거래 지원·기간 겹침 판정 | 거래별 식별자가 있는 형식만 지원(ADR-006) |
| 처리 자동 재claim·claim 세대 번호 | lease 만료 시 failed 종료 + 재업로드(ADR-008) |
| `deleting` 상태·토큰 만료 추적·삭제 작업 테이블·Storage 폴더 커서 | DB 즉시 삭제 + 고아 정리(ADR-009) |
| 결제 동기화 lease·세대 번호 | 조회 시작 시각 조건부 저장(ADR-012) |
| `data_revision` 읽기 전후 비교 | 요약은 `input_hash`로 신선도 판단 |
| `ai_summaries`의 Pro 전용 RLS, Storage 사용자 select 정책 | 본인 select만 / 정책 없음 |
| 데이터 없는 월 → 가장 가까운 월 리다이렉트 | 기본 월(최근 데이터 월)로 대체 |
| "이 달에 반영된 파일 n개" 표시 | 거래일 범위와 부분 데이터 안내 |
| UTF-16 CSV | UTF-8 → EUC-KR만 |
